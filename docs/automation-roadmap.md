# CLI・デバッグ機能の段階的な実装

目的は画面を見ずにGUI版と同じ実行状態を操作・検証できるようにすること。GUI・CLI・将来のMCPで操作の検証処理を共有し、シミュレーションも安全処理後の最終DMX値を使う。

## 第1段階: 常駐・接続の基盤

実装済み

- GUIへのローカル接続と、同じ `App` を使う画面なしの常駐。
- 状態・機材一覧・設定・最終DMX値の取得。
- 既存の属性・動き・エフェクト・色・シーン呼出などの操作。
- 保存と安全停止。実機送信なしでも40Hzの合成を継続。
- 接続中の監視と、必要な間だけ起動する40Hzのログ記録。
- 接続切断やGUI更新の停止に依存しない、リモートフラッシュの期限管理。

## 第2段階: GUI操作・編集の共通化

実装済み

- 操作対象の一覧と安定したID、ボタンのclick・press・release・hold。
- MIDI・キー・OSC入力の再現と、割り当ての検証。
- 機材、グループ、パッチ、機材定義、割り当て、シーン、チェイス、オート設定などの作成・編集・削除。
- 複数項目の変更の事前検証と一括反映、参照整合性の検査。
- 設定の再読込、差分、保存・復元。
- 機材・グループ追加、シーン保存・削除、割り当て削除、機材定義の保存・削除、プロジェクト読込と保存時の検証でGUIとCLIの共通処理を使用。

継続する作業

- GUIの数値・名前などの直接編集を、タブごとに共通の編集処理へ移行する。無効な入力途中の値を出力へ反映せず、入力欄の下書きとして保持する仕組みも必要。
- 使用中の機材定義のチャンネル構造変更は、現時点ではパッチを外して保存した後に行う。定義とプロジェクトを同時に移行する仕組みは今後の対象。
- 配列位置で指定するエフェクト・出力の編集には、第3段階で追加した設定バージョンによる競合検出を使う。

通常の操作から安全設定をバイパスできない方針を維持する。安全設定自体の編集を扱う場合は、演出操作と区別して仕様を決める。

## 第3段階: デバッグの自動化

実装済み

- 操作や設定項目の型・範囲・現在値を取得するスキーマ。
- 値の合成・上書き・安全補正を段階ごとに説明する `explain`。
- 操作の反映を待つ機能、拍・時刻・出力条件の待機と検証。
- GUIフレームで観測した設定・状態の変化と、MIDI・キー・OSC入力の記録。
- 記録の操作列・開始設定・機材定義を使った再現シナリオの出力。
- 設定バージョンと起動セッションによる、古い状態に基づく編集の拒否。
- GUI・常駐本体への接続、設定変更・保存・再読込、複数クライアントの再接続を含む結合試験。

残る作業

- GUIの観測履歴から個々の操作を再現する機能。現在は `state_change` を含む記録のシナリオ出力を拒否する。
- 実時間の拍の位相・進行中のフェード・音声や映像を含む実行状態の復元。
- 実機入力サービスの再接続と、大規模な機材構成での継続的な負荷測定。

## 将来の目標: 3Dプレビュー

描画機能の内製は保留し、別途開発されている [dmxsim](https://github.com/TechnoTUT/dmxsim) とのArt-Net接続を先に検証する。受信仕様、配布・起動方法、ライセンス、性能は連携前に確認する。

### 役割分担の案

- dmxctl: GUI・CLIによる操作、設定の検証、DMX合成と安全処理、記録、入力・シナリオの再現、出力値の検証。
- dmxsim: DMX値から機材の見た目を再現する処理、三次元の配置・向き・ビーム、表示品質と描画負荷の調整。
- 共通の接続仕様: ユニバース番号、開始アドレス、機材・モードとチャンネルの対応、16bit値、座標・角度の規約。どの情報を設定ファイルで共有するかも決める。

Art-Netで送るDMX値には、機材の配置やチャンネルの意味は含まれない。パッチと機材定義を渡す方法を検討し、3D固有の配置やビーム幅などの情報はdmxsim側で扱う案とする。

### 接続を検証する順序

1. dmxsimの対応機材・モード、受信ユニバース、起動方法を確認する。
2. 同じPCの `127.0.0.1:6454` にArtDmxを送り、既知の値で表示が一致するか確認する。機材を室内に並べたり、USB-DMX機器を接続する必要のない検証経路を作る。
3. 通常の実機出力とは独立した、プレビュー用Art-Net出力を追加する。現実装の `--output none` はArt-Netも止めるため、そのままでは外部ビューアーへ値を送れない。プレビューを使うために、保存済みのUSBやネットワーク出力をまとめて有効にする運用にはしない。
4. プレビューには安全処理後の最終DMX値を渡す。通常フレームだけでなく、ブラックアウト・停止時の安全値も対象にする。内部ユニバースとArt-Netの番号対応を明示し、実機向けの出力設定は変更しない。
5. GUI・CLIからビューアーを開く・閉じる・必要なら画像を保存する操作を整える。まず別プロセスでの連携を検証し、アプリ内の別ウィンドウとして組み込む方法は、dmxsimの構成を確認して決める。

### 維持する要件

- GUIから別ウィンドウで開いて確認できる操作感を目指す。
- 起動前は3D描画用の資源を確保しない。終了時は自分が起動した描画処理・プロセスの資源を解放する。
- 描画が遅れてもDMX出力を待たせず、最新の状態を表示する。
- 内蔵GPUで使えることを目標とし、基準PCと機材数を決めて性能を測定する。
- 機材ごとの角度やビーム幅など、表示のための追加情報と精度の限界を明示する。
- AIによる正確な出力値の検証は、内部スナップショット・ログを使う。UDP経由の受信・3D表示の確認とは分けて扱う。

サブモジュール化は、ソースからの同時ビルドや描画ライブラリの共有が必要かを確認してから決める。

## 将来の目標: MCP

- CLIと共通の操作APIへ接続するアダプターとして追加する。
- 操作一覧・引数の仕様・状態取得を提供し、実機送信や安全処理の条件も共通化する。
- MCPの接続を閉じても、GUI・常駐本体の実行は継続できる構成にする。
- 既存の制御用JSONプロトコルをMCPと呼ばず、導入時に仕様と互換性を検証する。
